# 未签收发放单逐单企微通知实施计划

## 摘要

- 保留现有 `SCM 未签收列表 -> 下载附件 -> 解压` 主流程，不再从邮件标题提取编号。
- 新增两段明确链路：`组装通知` 和 `企微群机器人发送`。每个未签收发放单单独通知一次。
- 发放单编号统一取 SCM 列表行里的 `send_number`，文本模版固定为：
  `@所有人【发放单提醒】`
  `本次发放单编号：{{send_number}}`
  `请相关人员前往 BPM 系统查阅核对，知悉办理～`
- 每条通知的文件来源沿用当前优先级：有 `下载1` 就只解压并发送 `下载1`，否则发送 `下载2` 的解压结果。

## 关键变更

- 配置结构收敛到单一路径：
  在 `scripts/email_config.py` 的 `AppConfig` 中新增 `wecom` 配置段，至少包含 `webhook`。
  `config.json.example` 同步新增该字段，并按你的明确要求填入当前 webhook 值。
  `config.json` 缺少 `wecom.webhook` 时直接报错，不保留“下载但不通知”的旧路径。

- 下载结果补全为“可通知结果”：
  调整 `scripts/scm_send_worker.py`，让当前解压步骤不仅落盘，还返回本次实际解压出的文件列表。
  `build_manifest_row(...)` 写入 `extracted_files` 和 `notification` 字段，便于 `run.json` 审计每个发放单下载了什么、发了什么、失败在哪一步。
  如果选中的压缩包不存在、解压失败、或解压后没有文件，则该发放单视为失败，不发送半成品通知。

- 新增企微通知模块：
  新建一个聚焦单职责的通知模块，例如 `scripts/wecom_notifier.py`。
  该模块只负责三件事：组装文本 payload、调用 webhook 发送文本消息、调用 `upload_media?type=file` 上传文件并再发送 `file` 消息。
  文本消息使用 `text` 类型，并显式传 `mentioned_list: ["@all"]`，不要只在正文里写 `@所有人`。
  文件消息按“先文本，后文件”的顺序串行发送；一个解压文件对应一条 `file` 消息，不做重新打包，不做批量合并。

- SCM 主流程内联通知：
  在 `scripts/run_send_record_downloads.py` 中把“下载/解压/通知”收敛成每条记录的完整处理单元。
  每处理完一个 `SendRecordRow`，立刻基于该行的 `send_number` 和解压文件列表发送企微通知，再继续下一条未签收记录。
  `scripts/email_listener.py` 继续只负责触发 SCM run，不再解析邮件标题编号。
  `run_send_record_downloads.py` CLI 同步改为要求提供 webhook 参数，避免仓库里同时维护“有通知”和“无通知”两套行为。

- 依赖与文档：
  `requirements.txt` 增加 `requests`，用于最小代码量完成 JSON POST 和 multipart 文件上传。
  `SKILL.md`、`config.json.example`、`CHANGELOG.md` 同步更新，所有示例命令都改成包含 webhook 配置/参数的版本。

## 公开接口与类型变更

- `AppConfig` 新增 `wecom: WecomConfig`。
- `config.json` / `config.json.example` 新增：
  ```json
  {
    "wecom": {
      "webhook": "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=..."
    }
  }
  ```
- `run_send_record_downloads.run(...)` 新增必填 webhook 入参，CLI 新增对应必填参数。
- `run.json` 的每条 `record` 新增：
  `extracted_files`: 实际解压出的文件路径列表
  `notification`: 文本发送、文件上传、文件发送的状态与错误信息

## 测试计划

- 配置测试：
  `tests/test_email_config.py` 验证 `wecom.webhook` 能正确读取，缺失时 fail fast。
- 通知模块测试：
  新增 `tests/test_wecom_notifier.py`，验证文本 payload 模版、`@all` 提醒参数、`upload_media -> send file` 顺序、多个解压文件逐个发送。
- 下载/解压测试：
  更新 `tests/test_scm_send_worker.py`，验证当前优先级仍是 `download1` 优先，其次 `download2`，并能返回解压文件列表。
- 主流程测试：
  更新 `tests/test_run_send_record_downloads.py`，验证每个未签收记录都会触发一次独立通知，编号来自 SCM 行的 `send_number`，不是邮件标题。
- 失败场景测试：
  覆盖 webhook 文本发送失败、文件上传失败、文件发送失败、解压后无文件四类场景，预期写入失败状态并中止当前 run。

## 默认假设

- 每个未签收发放单对应 1 条文本提醒消息，加上该发放单解压目录下的若干条 `file` 消息。
- 不引入重试队列、限流缓冲、异步并发发送；企微返回错误就立即失败，避免静默漏通知。
- 不改变当前“只解压一份压缩包”的业务规则；如果后续要同时发 `下载1` 和 `下载2`，那是下一次独立改动。
- `config.json.example` 写入真实 webhook 是按你的明确要求执行，但它会把敏感地址留在仓库历史里，这是已知风险，不在本次实现里再做兼容处理或安全兜底。
